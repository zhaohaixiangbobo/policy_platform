# 制度知识智能服务平台代办事项

> 文件说明：记录已确认但本轮明确不实施的后续建设事项。本文只描述目标、边界和验收条件，不代表功能已经上线。

## 1. 平台一致性对账机制

### 1.1 背景

平台业务库记录入库任务、审核和发布请求；Knowledge 库与 Qdrant 保存解析、分块、索引来源和当前 Alias 事实。外部服务抖动、进程中断或人工重试可能造成流程状态与实际生效状态暂时不一致，需要统一的对账能力。

### 1.2 建议架构

后续建立统一的 `ConsistencyCheckService`，让定时检查、管理员手动检查和业务事件检查复用同一套规则。服务分为两个明确阶段：

1. 只读检测：生成差异清单、严重级别、建议动作和证据，不修改任何状态。
2. 受控修复：管理员选择具体差异后执行幂等修复，并记录修复前后状态、操作人、时间和原因。

### 1.3 权威事实规则

- 制度是否正式上线，以 `index_profile.active_index_run_id` 及对应 `index_run_source` 为准。
- 只有 Alias 切换成功，IndexRun 才算正式发布。
- ParseRun、ChunkRun 和元数据修订是否可被索引，以 Knowledge 库中已批准的活动指针为准。
- Platform 的 `ingestion_job` 是业务流程与审计状态，不替代 Knowledge/Qdrant 的实际生效事实。
- 跨库不建立外键，通过版本化 ID、快照哈希和显式校验保持一致。

### 1.4 三种触发方式

#### 管理员手动触发（优先实施）

- 提供 Admin API、后台按钮和 CLI 命令。
- 默认执行只读检查；修复需要二次明确操作。
- 支持按任务、文档、IndexRun 或发布请求缩小范围。

#### 业务事件触发（第二步）

- 在任务失败、索引构建完成、Alias 切换完成和重试完成后执行定点只读检查。
- 检查失败不得覆盖原业务结果，应单独记录一致性告警。
- 不在状态回调中执行跨范围的全库自动修复。

#### 定时对账（基础设施稳定后实施）

- 待 Platform 切换 MySQL、明确多 Worker 部署方式后，再选用 APScheduler、Celery Beat 或外部调度器。
- 定时任务只负责调用统一服务，不复制对账规则。
- 调度频率根据真实故障数据确定，本阶段不冻结为每小时一次。

### 1.5 首批检查项

- active IndexRun 的 Qdrant collection 与 Alias 实际指向不一致。
- `index_run_source` 已包含文档，但对应任务仍停在 `FAILED` 或缺失 `index_run_id`。
- 发布请求显示成功，但 IndexRun 未 active；或 IndexRun 已 active，但发布请求未完成。
- Platform 发布绑定与 Knowledge 冻结来源不一致。
- 当前证据引用的 ParseRun/Node 已失效或快照哈希不匹配。

### 1.6 安全边界

- 不自动删除 collection、索引运行、审核记录或历史快照。
- 不根据 Platform 单边状态强制切换 Alias。
- 不把失败任务直接改成成功；修复前必须验证其文档确实进入当前 active IndexRun。
- 每次修复必须幂等、可审计，并输出明确的处理数量和未处理原因。

### 1.7 验收条件

- 同一差异由三种触发方式检测时得到一致结论。
- 只读检查不会修改数据库、Qdrant 或 Alias。
- 手动修复重复执行不会产生新副作用。
- 修复日志可追溯到操作者、目标对象、依据和前后状态。
- 真实外部服务不可用时返回可诊断结果，不把网络失败误判为数据不一致。

### 1.8 本轮决定

本轮不新增调度器、管理按钮、API、CLI、事件回调或自动修复逻辑，仅保留本代办记录。
