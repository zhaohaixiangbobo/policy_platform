## 1. 平台一致性对账机制

### 1.1 背景

平台业务库记录入库任务、审核和发布请求；Knowledge 库与 Qdrant 保存解析、分块、索引来源和当前 Alias 事实。外部服务抖动、进程中断或人工重试可能造成流程状态与实际生效状态暂时不一致，需要统一的对账能力。

### 1.2 建议架构

后续建立统一的 `ConsistencyCheckService`，让定时检查、管理员手动检查和业务事件检查复用同一套规则。服务分为两个明确阶段：

1. 只读检测：生成差异清单、严重级别、建议动作和证据，不修改任何状态。
2. 受控修复：管理员选择具体差异后执行幂等修复，并记录修复前后状态、操作人、时间和原因。

### 1.3 权威事实规则

- 制度是否正式上线，以 `index_profile.active_index_run_id` 及对应 `index_run_source` 为准。
- 只有 Alias 切换成功，IndexRun 才算正式发布。
- ParseRun、ChunkRun 和元数据修订是否可被索引，以 Knowledge 库中已批准的活动指针为准。
- Platform 的 `ingestion_job` 是业务流程与审计状态，不替代 Knowledge/Qdrant 的实际生效事实。
- 跨库不建立外键，通过版本化 ID、快照哈希和显式校验保持一致。

### 1.4 三种触发方式

#### 管理员手动触发（优先实施）

- 提供 Admin API、后台按钮和 CLI 命令。
- 默认执行只读检查；修复需要二次明确操作。
- 支持按任务、文档、IndexRun 或发布请求缩小范围。

#### 业务事件触发（第二步）

- 在任务失败、索引构建完成、Alias 切换完成和重试完成后执行定点只读检查。
- 检查失败不得覆盖原业务结果，应单独记录一致性告警。
- 不在状态回调中执行跨范围的全库自动修复。

#### 定时对账（基础设施稳定后实施）

- 待 Platform 切换 MySQL、明确多 Worker 部署方式后，再选用 APScheduler、Celery Beat 或外部调度器。
- 定时任务只负责调用统一服务，不复制对账规则。
- 调度频率根据真实故障数据确定，本阶段不冻结为每小时一次。

### 1.5 首批检查项

- active IndexRun 的 Qdrant collection 与 Alias 实际指向不一致。
- `index_run_source` 已包含文档，但对应任务仍停在 `FAILED` 或缺失 `index_run_id`。
- 发布请求显示成功，但 IndexRun 未 active；或 IndexRun 已 active，但发布请求未完成。
- Platform 发布绑定与 Knowledge 冻结来源不一致。
- 当前证据引用的 ParseRun/Node 已失效或快照哈希不匹配。

### 1.6 安全边界

- 不自动删除 collection、索引运行、审核记录或历史快照。
- 不根据 Platform 单边状态强制切换 Alias。
- 不把失败任务直接改成成功；修复前必须验证其文档确实进入当前 active IndexRun。
- 每次修复必须幂等、可审计，并输出明确的处理数量和未处理原因。

### 1.7 验收条件

- 同一差异由三种触发方式检测时得到一致结论。
- 只读检查不会修改数据库、Qdrant 或 Alias。
- 手动修复重复执行不会产生新副作用。
- 修复日志可追溯到操作者、目标对象、依据和前后状态。
- 真实外部服务不可用时返回可诊断结果，不把网络失败误判为数据不一致。

### 1.8 本轮决定

本轮不新增调度器、管理按钮、API、CLI、事件回调或自动修复逻辑，仅保留本代办记录。

## 2. 复杂问题分析模式

### 2.1 背景

问答输入区参考设计包含“深度思考”入口，但当前进程内 RAG 的 `generator_runtime_v2` 固定关闭模型 thinking，查询契约也没有对应模式。仅增加前端按钮不会改变检索或生成行为，属于无真实能力支撑的界面功能。

### 2.2 后续设计方向

- 产品名称使用“复杂问题分析”，不向用户承诺或展示模型内部 reasoning。
- 公开请求使用版本化业务字段，例如 `answer_mode=STANDARD|DEEP`，不直接暴露模型供应商的 thinking 参数。
- `STANDARD` 保持现有检索、严格 JSON Schema、质量门禁和三种回答状态不变。
- `DEEP` 使用独立、可审计的检索与生成配置版本，可按评测结果增加跨制度比较、查询分解、证据复核或生成预算。
- Platform 应用层仍只调用进程内 `KnowledgeService` 的版本化查询契约，不绕过服务读取知识 SQLite、Qdrant、模型客户端或受控诊断数据。
- 公开响应仍只包含 `ANSWER / INSUFFICIENT_EVIDENCE / CONFLICT`、版本化 Citation 和公开质量门禁摘要，不返回 reasoning、Prompt 或完整上下文。

### 2.3 前置条件

- 建立复杂问题测试集，并与标准模式比较答案正确性、Citation 支撑率和冲突处理质量。
- 完成进程内 RAG 暖态延迟、单查询线程排队和并发影响测试，再决定是否开放、默认关闭方式及用户提示。
- 明确独立配置版本、审计字段、失败降级和取消等待语义。
- 进程内查询契约先完成向后兼容扩展，Platform 应用层再接入该字段。

### 2.4 验收条件

- 关闭复杂问题分析时与现有问答行为完全一致。
- 开启后能够通过公开快照确认实际使用了独立模式，而不是前端视觉状态。
- 两种模式均通过三种回答状态、Citation、质量门禁和敏感诊断数据防泄漏测试。
- 外部服务失败时返回稳定错误或保守降级，不回退为未受控的普通生成。

### 2.5 本轮决定

本轮不增加“深度思考”按钮，不修改 RAG 生成配置或模型调用；待上述前置条件满足后作为独立里程碑实施。

## 3. 首份历史制度检索验收

### 3.1 当前事实

2026-09-14 检查 active IndexRun 7 时，当前正式快照包含 11 份现行有效制度；Qdrant Alias
中的 325 个 point 全部属于该 IndexRun，历史状态 point 为 0。因此 `HISTORICAL` 请求契约、过滤逻辑和界面禁用状态已经具备，
但尚无真实历史制度可完成端到端召回验收。

### 3.2 后续验收步骤

1. 通过正式元数据治理流程将一份具体制度版本登记为已废止或已失效并审核通过；
2. 构建全量 IndexRun，确认该版本进入 `index_run_source`，且 Qdrant payload 的
   `document_status` 为 `repealed` 或 `expired`；
3. Alias 切换成功后，确认 `/api/v1/chat/query-capabilities` 的历史制度数量大于零；
4. 使用 `HISTORICAL + SELECTED` 查询该具体 `document_id`，验证可以召回；
5. 使用 `CURRENT + SELECTED` 查询同一历史版本，验证被状态边界拒绝；
6. 验证返回 Citation 的 `document_id`、状态及各类 run ID 均在 Platform 本轮范围快照内。

### 3.3 安全边界

- 不为测试修改现有正式制度状态；使用后续真实废止业务或专门验收数据。
- 历史制度必须实际进入 active Qdrant 索引，不能只在前端显示选项。
- 指定历史制度无结果时不得自动回退到全部制度或现行制度。
